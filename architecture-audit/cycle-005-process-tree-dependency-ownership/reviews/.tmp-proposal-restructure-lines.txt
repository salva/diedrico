     1	# Wave 005 Proposal Restructure — Higher-level use-case extraction considered, but too broad for Wave 005
     2	
     3	## Summary
     4	
     5	This proposal records the higher-level alternative considered for Wave 005: introducing a narrow application/domain boundary for process-history UI actions while deleting deprecated process/dependency APIs. After round-01 review, this proposal is intentionally positioned as a **rejected alternative for Wave 005 implementation** rather than the recommended path. Its dependency-boundary deletion insight is folded into Proposal Direct, but its mandatory `ActionsPanel.vue` process-history use-case extraction is deferred to Wave 006 because it crosses into the broader UI command-construction refactor.
     6	
     7	The useful architectural observation remains: `ActionsPanel.vue` directly imports concrete process-tree operations and should eventually dispatch user intent through an application use-case/controller seam. The wave-ordering correction is that Wave 005 can achieve its central target—`ProcessTree` owns construction history only and `DependencyService` owns dependency graph queries—without introducing that UI seam now.
     8	
     9	## Target outcome if this alternative were chosen
    10	
    11	If intentionally selected despite the scope risk, implementation would produce:
    12	
    13	- `ProcessTree` as a pure construction-history data structure with no implicit insertion API and no dependency-query API.
    14	- `DependencyService` as the only geometric dependency query/update boundary, with no process-era rebuild/action-dependency placeholders.
    15	- A small process-history application boundary that owns command construction for panel-level process-tree UI actions.
    16	- `ActionsPanel.vue` no longer importing concrete process-tree operations directly for subprocess/panel controls.
    17	- Tests setting up process history through explicit process-history commands/use-cases rather than deprecated direct tree mutation.
    18	
    19	## Why this is not the recommended Wave 005 implementation
    20	
    21	Round-01 review identified that the use-case extraction is architecturally plausible but poorly placed in the wave sequence:
    22	
    23	- Wave 005's core objective is ownership cleanup inside process-tree/dependency domain boundaries: delete implicit process insertion, delete process-tree dependency queries, delete no-op dependency compatibility shims, and rewrite stale tests.
    24	- Wave 006 is explicitly responsible for UI command-construction extraction across panels, tools, canvas, and toolbar surfaces. Extracting only `ActionsPanel.vue` now risks creating a one-off seam that Wave 006 must revisit or replace.
    25	- The current `ActionsPanel.vue` direct operation imports are a real cross-layer leak, but they are not required to remove `ProcessTree.addAction()`, `World.addAction()`, `ProcessTree.getActionsDependingOnElement()`, `DependencyService.rebuildDependencyMaps()`, or `DependencyService.getActionDependencies()`.
    26	- A partial use-case module could become an anemic wrapper around existing component code if introduced before the broader UI command-controller shape is designed.
    27	
    28	Therefore, for Wave 005 this proposal should serve as decision context and future-Wave input, not as the implementation baseline. Any adoption of the use-case extraction in Wave 005 would be a deliberate scope expansion requiring decision sign-off.
    29	
    30	## Conceptual design retained for Wave 006 consideration
    31	
    32	A later Wave 006 design may create a module such as `frontend/src/application/processTree/processHistoryUseCases.ts` or a broader UI command-controller layer exposing typed functions over `{ world, commandStack }` or narrower ports:
    33	
    34	- `pushSubprocess(world, commandStack, input)`
    35	- `popSubprocess(world, commandStack)`
    36	- `renameSubprocess(world, commandStack, input)`
    37	- `toggleSubprocessEncapsulation(world, commandStack, input)`
    38	- `toggleOutput(world, commandStack, input)`
    39	- Explicit process-history setup helpers for tests only if they do not become production compatibility shims.
    40	
    41	This later boundary should be solved alongside `SvgCanvas.vue`, toolbar/tool handlers, and other UI command-construction surfaces so it does not create a one-panel architecture.
    42	
    43	## Dependency boundary hardening still belongs in Wave 005
    44	
    45	The review agreed that deleting `DependencyService` compatibility shims belongs in Wave 005 and should not wait for this restructure alternative. Proposal Direct now includes this deletion.
    46	
    47	Wave 005 should delete:
    48	
    49	- `DependencyService.rebuildDependencyMaps()` deprecated no-op (`frontend/src/domain/world/DependencyService.ts:130-131`).
    50	- `DependencyService.getActionDependencies(_actionId)` process-era placeholder/comment block (`frontend/src/domain/world/DependencyService.ts:306-317`).
    51	
    52	Tests that call `rebuildDependencyMaps()` should be rewritten to use actual world/plane element registration or explicit `DependencyService.registerNode(...)` setup. If a deletion/factory test depends on rebuild semantics, that is evidence of hidden process/dependency coupling and should be fixed in Wave 005 through the real dependency graph boundary, not by retaining a compatibility shim.

   174	## Risks
   175	
   176	- This proposal overlaps with Wave 006 by removing direct process-tree operation construction from `ActionsPanel.vue`. The corrected recommendation avoids that risk by deferring extraction.
   177	- Deleting `DependencyService.rebuildDependencyMaps()` may require rewriting stale tests that used it as a fixture convenience. If those tests reveal real missing dependency registration, fix the registration path rather than restoring a rebuild shim.
   178	- Introducing a use-case module could create a new anemic wrapper if it merely renames existing component code. This is the main reason the extraction should wait for Wave 006's broader UI command-construction design.
   179	- Existing validation debt from earlier waves can still block lint/build/e2e execution; implementation logs must distinguish attributable failures from known tooling/test corruption.
   180	
   181	## Why this may be the better long-term fix
   182	
   183	Proposal Direct deletes the deprecated APIs but leaves the nearest active UI path (`ActionsPanel.vue`) importing concrete process-tree operations. The baseline and current scope both identify UI-to-operation imports as a cross-layer leak. A later Wave 006 should solve that leak with a consistent application/use-case or controller boundary, not by leaving it indefinitely.
   184	
   185	## Why this is too broad for Wave 005
   186	
   187	Wave 006 is explicitly responsible for moving UI command construction into application use-cases/tool controllers. Wave 005 can complete its central process-tree/dependency ownership cleanup by deleting deprecated domain/dependency APIs and stale tests now. Pulling `ActionsPanel.vue` use-case extraction into this wave would blend two waves, increase blast radius, and risk hidden implementation scope creep. Therefore this proposal should not be selected for Wave 005 unless the decision deliberately accepts that scope expansion.
