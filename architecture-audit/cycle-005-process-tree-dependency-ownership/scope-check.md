# Wave 005 Scope Check — Process-tree/dependency ownership

**Cycle:** `cycle-005-process-tree-dependency-ownership`  
**Stage:** `cycle-005-fresh-scout-proposals`  
**Source-code changes in this stage:** none.  
**Conclusion:** Wave 005 can proceed without a `wave-plan.md` edit. Waves 001–004 make this wave more central, not less: `DependencyService` is now domain-local, command/persistence restoration is typed enough to safely remove deprecated process-tree APIs, and legacy store/workspace state no longer competes with `World`/`ProcessTree`.

## Wave-plan entry re-read

Wave 005 targets `frontend/src/domain/processTree/ProcessTree.ts`, `frontend/src/domain/processTree/Action.ts` and action creators, the dependency graph/service boundary after Wave 001, process-tree operations under `frontend/src/commands/operations/processTree/`, `ActionsPanel.vue` only as needed, and focused process-tree/dependency/undo/redo/actions-panel tests (`architecture-audit/wave-plan.md`, Wave 005). Its stated target remains correct: `ProcessTree` should own construction history only; dependency queries should live in the single dependency boundary; UI panels should avoid deprecated direct process/dependency APIs where in scope.

## Effects of Waves 001–004 on this scope

### Wave 001 — dependency boundary is now domain-local

Wave 001 deleted the old service-layer `frontend/src/services/DependencyService.ts` path and moved the class to `frontend/src/domain/world/DependencyService.ts` without a compatibility shim (`architecture-audit/cycle-001-invert-world-application-boundary/implementation-log.md`). Current `World` imports `ProcessTree` and the domain-local `DependencyService` side-by-side (`frontend/src/domain/world/World.ts:95`, `frontend/src/domain/world/World.ts:96`), constructs both in the constructor (`frontend/src/domain/world/World.ts:177`, `frontend/src/domain/world/World.ts:178`), resets both in `clear()` (`frontend/src/domain/world/World.ts:253`, `frontend/src/domain/world/World.ts:254`), and exposes them through `getProcessTree()` and `getDependencyService()` (`frontend/src/domain/world/World.ts:892`, `frontend/src/domain/world/World.ts:898`). This confirms Wave 005 should treat dependency lookup as a single `World.getDependencyService()` boundary, not as a process-tree responsibility.

### Wave 002 — projection planes register dependencies through the same boundary

Wave 002 split `ProjectionPlane.ts` and introduced projection-plane context interfaces while keeping dependency registration through `getDependencyService()` (`architecture-audit/cycle-002-split-projection-plane-domain-god-module/implementation-log.md`). Current extracted plane storage calls `context?.getDependencyService().registerNode(...)` and `unregisterNode(...)` for points, lines, and circles (`frontend/src/domain/world/projectionPlane/ProjectionPlaneElementStore.ts:31`, `frontend/src/domain/world/projectionPlane/ProjectionPlaneElementStore.ts:41`, `frontend/src/domain/world/projectionPlane/ProjectionPlaneElementStore.ts:53`, `frontend/src/domain/world/projectionPlane/ProjectionPlaneElementStore.ts:62`, `frontend/src/domain/world/projectionPlane/ProjectionPlaneElementStore.ts:74`, `frontend/src/domain/world/projectionPlane/ProjectionPlaneElementStore.ts:83`). This strengthens the premise that element dependency edges are no longer process-tree data.

### Wave 003 — no legacy store/workspace process-state path remains

Wave 003 deleted `worldStore`, dead workspace components, obsolete geometry composables, and legacy `ElementTypes` (`architecture-audit/cycle-003-authoritative-world-state-delete-dead-store-workspace/implementation-log.md`). Process UI state that remains is collapse/expansion state in `processTreeStore`, while construction history remains in `World.getProcessTree()`. Current `ActionsPanel.vue` injects `world`, calls `world.getProcessTree()`, and uses `processTreeStore` only for collapsed/expanded UI state (`frontend/src/components/panels/ActionsPanel.vue:75`, `frontend/src/components/panels/ActionsPanel.vue:77`, `frontend/src/components/panels/ActionsPanel.vue:86`, `frontend/src/components/panels/ActionsPanel.vue:175`). Wave 005 therefore does not need to preserve any legacy store-backed construction-history path.

### Wave 004 — command/persistence contract is ready for process-tree API deletion

Wave 004 added typed operation descriptors/registry restoration, command snapshots, committed-history restoration, and removed private persistence casts/migrations (`architecture-audit/cycle-004-command-undo-persistence-contract/implementation-log.md`). Current process-tree operation descriptors are centralized in `registerProcessTreeOperationDescriptors.ts`, including `AddProcessTreeActionOp`, `AddProcessTreeActionGroup`, subprocess stack, rename, encapsulation/output toggles, and remove/restore operations (`frontend/src/commands/operations/processTree/registerProcessTreeOperationDescriptors.ts:20`, `frontend/src/commands/operations/processTree/registerProcessTreeOperationDescriptors.ts:21`, `frontend/src/commands/operations/processTree/registerProcessTreeOperationDescriptors.ts:29`, `frontend/src/commands/operations/processTree/registerProcessTreeOperationDescriptors.ts:33`, `frontend/src/commands/operations/processTree/registerProcessTreeOperationDescriptors.ts:37`, `frontend/src/commands/operations/processTree/registerProcessTreeOperationDescriptors.ts:41`, `frontend/src/commands/operations/processTree/registerProcessTreeOperationDescriptors.ts:45`, `frontend/src/commands/operations/processTree/registerProcessTreeOperationDescriptors.ts:49`, `frontend/src/commands/operations/processTree/registerProcessTreeOperationDescriptors.ts:53`). That gives Wave 005 a stable place to update serialization/restoration if process-tree operation surfaces are renamed or tightened.

## Current evidence that Wave 005 premises still hold

### Deprecated process-tree insertion remains active

`ProcessTree.addAction(action, groupName?)` still exists and is explicitly marked deprecated because it implicitly creates action groups and has historically broken undo logic (`frontend/src/domain/processTree/ProcessTree.ts:143`, `frontend/src/domain/processTree/ProcessTree.ts:144`, `frontend/src/domain/processTree/ProcessTree.ts:145`, `frontend/src/domain/processTree/ProcessTree.ts:148`, `frontend/src/domain/processTree/ProcessTree.ts:150`). `World.addAction(action: any, groupName?: string): any` remains as a loose proxy to that deprecated path (`frontend/src/domain/world/World.ts:904`, `frontend/src/domain/world/World.ts:907`, `frontend/src/domain/world/World.ts:908`).

Active tests still encode the obsolete implicit-group path: `frontend/tests/unit/processTree.spec.ts` calls `tree.addAction(...)` in multiple tests for single action insertion, group-name creation, chronological ordering, recursive traversal, removing an action, and output collection (`frontend/tests/unit/processTree.spec.ts:36`, `frontend/tests/unit/processTree.spec.ts:47`, `frontend/tests/unit/processTree.spec.ts:59`, `frontend/tests/unit/processTree.spec.ts:97`, `frontend/tests/unit/processTree.spec.ts:115`, `frontend/tests/unit/processTree.spec.ts:140`, `frontend/tests/unit/processTree.spec.ts:161`, `frontend/tests/unit/processTree.spec.ts:172`). Deletion/factory tests also bypass command-tracked group creation by calling `world.getProcessTree().addAction(...)` directly (`frontend/tests/unit/commands/factories/DeletionSequenceFactory.spec.ts:55`, `frontend/tests/unit/commands/factories/DeletionSequenceFactory.spec.ts:86`, `frontend/tests/unit/commands/factories/DeletionSequenceFactory.spec.ts:87`, `frontend/tests/unit/commands/factories/DeletionSequenceFactory.spec.ts:88`; `frontend/tests/unit/commands/removeElementOps.spec.ts:43`). These tests are obsolete under the wave target and should be rewritten or deleted.

### Deprecated process-tree dependency query remains as a stub

`ProcessTree.getActionsDependingOnElement(elementId)` still exists, is documented as deprecated in favor of `DependencyService.getDependents(elementId)`, logs a warning, and returns an empty array (`frontend/src/domain/processTree/ProcessTree.ts:401`, `frontend/src/domain/processTree/ProcessTree.ts:403`, `frontend/src/domain/processTree/ProcessTree.ts:404`, `frontend/src/domain/processTree/ProcessTree.ts:406`, `frontend/src/domain/processTree/ProcessTree.ts:407`, `frontend/src/domain/processTree/ProcessTree.ts:411`, `frontend/src/domain/processTree/ProcessTree.ts:412`). Its unit tests are already skipped because dependencies are no longer stored in actions (`frontend/tests/unit/processTree.spec.ts:179`, `frontend/tests/unit/processTree.spec.ts:180`, `frontend/tests/unit/processTree.spec.ts:184`, `frontend/tests/unit/processTree.spec.ts:188`). This is dead compatibility surface and should be deleted, not wrapped.

### DependencyService is the active dependency boundary but still has no-op compatibility residue

`DependencyService` is now a domain-local stateful container (`frontend/src/domain/world/DependencyService.ts:42`, `frontend/src/domain/world/DependencyService.ts:49`). It owns node registration/unregistration, dependency queries, dependent traversal, and invalidation traces (`frontend/src/domain/world/DependencyService.ts:67`, `frontend/src/domain/world/DependencyService.ts:90`, `frontend/src/domain/world/DependencyService.ts:150`, `frontend/src/domain/world/DependencyService.ts:180`, `frontend/src/domain/world/DependencyService.ts:278`). However, it also keeps deprecated no-op process-era methods such as `rebuildDependencyMaps()` and `getActionDependencies(_actionId)` (`frontend/src/domain/world/DependencyService.ts:130`, `frontend/src/domain/world/DependencyService.ts:131`, `frontend/src/domain/world/DependencyService.ts:306`, `frontend/src/domain/world/DependencyService.ts:317`). Tests still call `world.getDependencyService().rebuildDependencyMaps()` in deletion scenarios (`frontend/tests/unit/commands/factories/DeletionSequenceFactory.spec.ts:93`, `frontend/tests/unit/commands/factories/DeletionSequenceFactory.spec.ts:132`, `frontend/tests/unit/commands/factories/DeletionSequenceFactory.spec.ts:168`, `frontend/tests/unit/commands/factories/DeletionSequenceFactory.spec.ts:264`, `frontend/tests/unit/commands/factories/DeletionSequenceFactory.spec.ts:312`; `frontend/tests/unit/commands/removeElementOps.spec.ts:132`). These no-op dependency shims are in scope for Proposal Restructure and may be included in Proposal Direct if the reviewer agrees they are part of the same ownership cleanup.

### Explicit action-group insertion is already the real operation path

The current operation sequence already separates action-group creation from action insertion. `AddProcessTreeActionGroupOp.apply()` calls `processTree.addActionGroup(this.group)` and its undo removes the group (`frontend/src/commands/operations/processTree/AddProcessTreeActionGroupOp.ts:23`, `frontend/src/commands/operations/processTree/AddProcessTreeActionGroupOp.ts:26`, `frontend/src/commands/operations/processTree/AddProcessTreeActionGroupOp.ts:39`, `frontend/src/commands/operations/processTree/AddProcessTreeActionGroupOp.ts:40`). `AddProcessTreeActionOp.apply()` calls `processTree.addActionToGroup(this.action, this.groupId)` and its undo removes the produced action node (`frontend/src/commands/operations/processTree/AddProcessTreeActionOp.ts:32`, `frontend/src/commands/operations/processTree/AddProcessTreeActionOp.ts:34`, `frontend/src/commands/operations/processTree/AddProcessTreeActionOp.ts:62`, `frontend/src/commands/operations/processTree/AddProcessTreeActionOp.ts:63`). Its comment already says the old fallback was removed and group lifecycle is handled by `AddProcessTreeActionGroupOp` (`frontend/src/commands/operations/processTree/AddProcessTreeActionOp.ts:61`). Factories use this explicit path, for example `PointSequenceFactory` adds `AddProcessTreeActionOp(action, groupId)` (`frontend/src/commands/factories/PointSequenceFactory.ts:48`) and the initializer creates an action group with `AddProcessTreeActionGroupOp` before initialization actions (`frontend/src/application/world/initializeWorld.ts:27`, `frontend/src/application/world/initializeWorld.ts:28`).

### ActionsPanel is still a direct operation-construction UI surface

`ActionsPanel.vue` imports concrete process-tree operations directly (`frontend/src/components/panels/ActionsPanel.vue:56`, `frontend/src/components/panels/ActionsPanel.vue:57`, `frontend/src/components/panels/ActionsPanel.vue:58`, `frontend/src/components/panels/ActionsPanel.vue:59`, `frontend/src/components/panels/ActionsPanel.vue:60`) and executes commands from component handlers. It reads `processTree.value.getAllActions()` to search for an action by produced element ID, then carries a comment saying dependencies are now in `DependencyService` (`frontend/src/components/panels/ActionsPanel.vue:228`, `frontend/src/components/panels/ActionsPanel.vue:236`). It also logs process-tree state in normal component lifecycle (`frontend/src/components/panels/ActionsPanel.vue:88`, `frontend/src/components/panels/ActionsPanel.vue:131`, `frontend/src/components/panels/ActionsPanel.vue:143`, `frontend/src/components/panels/ActionsPanel.vue:150`, `frontend/src/components/panels/ActionsPanel.vue:167`, `frontend/src/components/panels/ActionsPanel.vue:180`). The operation imports are mostly a broader Wave 006 UI/use-case concern, but the dependency lookup and debug/noisy remnants are in scope if the implementation touches ActionsPanel behavior.

## Re-rank of remaining waves after Waves 001–004

No reordering is needed. Current centrality remains:

1. **Wave 005** — delete deprecated process-tree/dependency overlap now that command/persistence and dependency boundaries are stable.
2. **Wave 006** — move UI command construction into application use-cases/tool controllers; ActionsPanel direct operation construction is a known dependent problem but should not be solved broadly before the process APIs are clean.
3. **Wave 007 / Wave 008** — rendering selectors/adapters after process/use-case boundaries are clearer.
4. **Wave 009** — app shell services after command/use-case/rendering surfaces settle.
5. **Wave 010–013** — backend contract, architecture tests/root gates, debug/placeholders, and docs after structural boundaries are established.

## Scope decision

Wave 005 can proceed without a wave-plan edit.

The strongest direct implementation target is to delete `ProcessTree.addAction()`, delete `World.addAction()`, delete `ProcessTree.getActionsDependingOnElement()`, rewrite/delete tests that encode implicit group creation, and tighten process-tree tests around `addActionGroup()` + `addActionToGroup()` and operation-mediated insertion. The restructure alternative should evaluate removing remaining no-op dependency shims and introducing a small process-history application boundary that ActionsPanel can call, but the implementation should avoid pulling all Wave 006 UI command-controller work into Wave 005 unless review explicitly chooses that higher-level fix.
